# 25 — HR System: Threat Model (STRIDE) and Evidence

Scope: the HR modules (employees, leave, attendance, payroll) on top of the IAM threat model in `10-security-and-threat-model.md`. "Evidence" names the automated test that fails if the control is removed. **An independent penetration test is still required before go-live [open].**

| # | Threat | Control | Evidence |
|---|---|---|---|
| S1 | Someone signs in as another employee and reads their payslip | payslips are looked up by *your* employee id only; another person's slip returns 404; slips exist for employees only after the run is locked | `HrPayrollTests.Payroll_data_needs_the_permission…`, `HrAuthorizationSweepTests.Other_peoples_data…` |
| T1 | Pay run altered after approval (insider, bug, SQL) | locked/paid runs refused by service **and** database triggers (items, lines, run totals, delete, reopen) | `HrPayrollTests.A_locked_run_cannot_be_changed_through_the_api_or_the_database` |
| T2 | Salary or tax data changed without trace | every change audited with before/after as "[changed]", never values; effective-dated history kept | `HrEmployeeTests`, `HrPayrollTests` (audit assertions) |
| T3 | Stale numbers approved | any added/removed line sends a Calculated run back to Draft | `HrPayrollTests.Extra_lines_change_the_result…` |
| R1 | "I did not approve that payroll" | approve, lock, paid, bank-file, register, compensation views are audited with the actor; maker ≠ checker is enforced and the attempt is audited | `HrPayrollTests.The_person_who_calculated_cannot_approve…` |
| I1 | Salary / NIK / NPWP / bank account readable from a database dump or backup | AES-GCM per field, bound to row and column (AAD), key outside the database | `HrPayrollTests.A_monthly_run_matches…` (ciphertext does not contain the value), `HrEmployeeTests.Sensitive_fields…` |
| I2 | Sensitive values leak into logs, audit or exports | audit stores "[changed]" only; CSV export carries no protected fields; formula injection neutralised | `HrEmployeeTests.Sensitive_fields…`, `…export_neutralises_spreadsheet_formulas` |
| I3 | A manager or employee reads data of people they do not manage | server-side checks (manager sees direct reports only; other people's records 403/404) | `HrLeaveTests.Only_the_direct_manager…`, `HrAuthorizationSweepTests` |
| I4 | Any HR endpoint added later without a permission | sweep over the real routing table: unguarded routes must be on a short named list; ordinary user gets 403 on all permission-gated routes; signed-out gets 401 on all | `HrAuthorizationSweepTests` |
| D1 | Large file or huge import exhausts the server | import capped (1,000 rows, 1 MB), all-or-nothing, validated before write; paging capped at 100 (500 for calendar) | `HrEmployeeTests.Import_*` |
| D2 | Double spend of leave days by concurrent requests | row lock per employee + unique grant constraint | `HrLeaveTests.Two_simultaneous_requests…`, `…Concurrent_balance_reads…` |
| E1 | HR admin lifts own privileges into payroll | payroll permissions are separate roles; permission changes need `permissions.assign` + recent reauth (IAM) | `AuthorizationTests`, `RoleAdminTests` |
| E2 | One person prepares, approves and pays | calculator cannot approve or lock; `payroll_officer` has no approve/lock; the bank file needs the lock permission | `HrPayrollTests` |
| E3 | Stolen session used for payroll actions | every payroll endpoint and every protected-field read/write needs a password check in the last 5 minutes | `HrPayrollTests`, `HrEmployeeTests` |
| E4 | Employee terminated but still signed in | ending employment deactivates the account and revokes every session | `HrEmployeeTests.Ending_employment_deactivates…` |

| E5 | Delegation used to widen power | a delegate must already hold the approval permission; delegation moves scope only, is time-boxed (90 days), revocable, audited | `HrOpsTests.A_delegate_decides…` |
| T4 | Bank account swapped through a hijacked session (payroll fraud) | bank/tax/national-ID changes are requests: fresh password check to ask, HR approval (with the sensitive permission and fresh check) to apply, values stored encrypted and never audited | `HrSelfServiceTests.Contact_details_change_directly…` |
| I5 | Someone reads another person's personal data through the export | the export contains only the signed-in person's own record, behind a fresh password check | `HrSelfServiceTests.The_personal_data_export…` |
| T5 | Erasure used to rewrite payroll evidence | only names on pay-run items can change, only inside the anonymising transaction, with every figure and the employee link unchanged; raw SQL otherwise still refused | `HrSelfServiceTests.Anonymisation_erases_identity…` |
| I6 | Uploaded file executes or lies about its type | type decided from file bytes (PDF/PNG/JPEG), size capped, names cleaned, served as attachment | `HrOpsTests.Documents_are_typed…` |
| T6 | Machine-import used to forge attendance | needs attendance-manage + fresh password check, closed months refused, existing days never overwritten, audited | `HrOpsTests.Machine_punches…` |

| I7 | Webhook used to reach internal services (SSRF) or to leak data | https + public addresses only (saved URL checked, and the address actually connected to is checked again, defeating DNS tricks), no redirects, 10 s timeout, payloads carry ids/codes only, management needs `hrconfig.manage` + fresh password check | `HrWebhookTests` |
| T7 | Forged or replayed webhook calls to the receiver | HMAC-SHA256 over `timestamp.body` with a per-endpoint secret (encrypted at rest, shown once, rotatable); the receiver should reject old timestamps | `HrWebhookTests.Events_are_queued…` |

| T8 | Payroll rates/tax tables changed to skim or to hide a mistake | a change is a new version (never an edit): re-authentication + `payroll.configure`, mandatory reason, only from the 1st of a month no locked run covers, one per month, old→new values audited; a pay run stores the exact rules it used and re-reads them only until it is locked (the DB trigger freezes the rest) | `HrPayrollTests.A_rules_correction_applies…` |
| T9 | A pay run mixes up companies (wrong NPWP on the tax file, a person paid twice) | one run per company per month (unique index), a run only covers its own company's people (service-enforced, also for manual lines, THR and severance), moving a person is refused while they sit in an unfinished run, a locked run's company is frozen by the DB trigger | `HrPayrollTests.Each_company_runs_its_own_payroll…` |
| I8 | Notification used to phish or to leak another person's messages | each person reads and marks only their own (queries are filtered by the caller's user id, not by an id in the URL); only in-app paths (`/…`, never `//` or full URLs) are stored; bodies carry short text, no salary figures | `HrNotificationTests` |

| T10 | A malicious file uploaded as a document or receipt | type decided from the file's own bytes (PDF/PNG/JPEG only), size capped, and with `Antivirus__Enabled` every upload is streamed to ClamAV first: infected → refused and audited; scanner unreachable → refused (fail closed). Files are stored as bytes and always downloaded as attachments with their true type | `HrOpsTests.A_new_version_replaces…`, `ClamAvScannerTests` |
| T11 | Expense-claim fraud (approving your own claim, paying a claim twice, opening colleagues' receipts) | nobody decides their own claim; deciding needs the manager relation or `claims.manage`; an approved claim becomes one tax-free line in one unlocked run and is marked paid only when that run locks, after which it is never picked up again; receipts open only for the owner and the deciders, audited | `HrPayrollTests.An_approved_expense_claim…` |
| S3 | A forged employment letter | letters are numbered (`SKK/year/n`, unique), the facts are frozen at approval, issuing and every download are audited; the PDF tells the reader to confirm the number with HR. It is **not** digitally signed | `HrWorkspaceTests.An_employment_letter…` |
| E3 | Bulk approval used to push through requests the caller could not decide one by one | the bulk endpoint only loops over the same per-request services, each with its own permission, ownership and state checks; results are reported per item | `HrWorkspaceTests.The_inbox_shows_only…` |
| I9 | Metrics or the API description leak data or widen the attack surface | `/health/metrics` exists only with a ≥ 24-character token and answers 404 otherwise; labels carry route templates, never ids; values are counts. The OpenAPI document needs a sign-in and can be switched off (`Api__OpenApi=false`); it describes shapes, not data | `ApiDescriptionAndMetricsTests` |
| I10 | Location tracking of employees | a position is asked for only when work locations exist and the person says "at the office", stored rounded, used for a flag; refusing still clocks in. Working from home records no position | `HrOpsTests.Clock_in_records_where_people_work…` |
| T12 | A manager approves long leave alone where policy wants HR too | per leave type, requests from N days need HR after the manager; the manager's approval only moves it on, and the manager cannot decide it again | `HrLeaveTests.Long_leave_of_a_type_that_needs_HR…` |

| S4 | A stolen or guessed provisioning (SCIM) token creates or disables accounts | tokens are 256-bit random, stored only as a hash, shown once, named, revocable at once, at most 5 active, created only by `settings.manage` after a fresh password check; a token works in one organisation only; provisioned users get the plain `user` role (no privilege comes from outside); DELETE deactivates and never erases; the last active super admin cannot be switched off; every change is audited as `scim:<token name>` | `ScimTests` |
| E4 | SCIM used to reach another organisation's users or to learn who exists | every query runs inside the token's organisation; an unsupported filter is refused instead of ignored; a duplicate e-mail answers "exists" without saying where | `ScimTests.A_token_sees_only_its_own_organisation…` |
| T13 | Weekly pay changed after approval, paid twice, or never reconciled with tax and BPJS | preparer ≠ approver; approved payouts are frozen by the service and by database triggers (amounts, week, company, reopening, deletion); the monthly run deducts each weekly payment once and marks it settled when it locks; unsettled payments stay visible | `HrPayrollTests.Daily_wage_workers_can_be_paid_weekly…` |

## Known gaps (accepted for now, tracked)
- Payroll rule values (TER, PTKP, BPJS rates and caps) are now editable data with versions (see T8), but the **built-in values are unvalidated by a tax consultant [open]**, as are the daily-wage assumptions (TER for daily workers, overtime multiplier 25 × daily wage, no minimum-wage check).
- Run item amounts are stored as plain numbers (needed for totals); protected by permission, audit and disk encryption, not field encryption.
- Virus scanning needs a ClamAV daemon and `Antivirus__Enabled=true`; without it uploads are only type-checked. Files are stored in the database (fine for contracts, ID scans and receipts, not for large archives).
- Employment letters and payslips are not digitally signed; authenticity rests on the number/audit trail.
- Back-dated pay changes do not reopen BPJS for the past months (decision for the consultant); weekly pay is an interim payment settled monthly (not a separate weekly tax withholding); SCIM provisions users only, not groups.
- Dependency audit: .NET packages clean; `npm audit` reports 0 vulnerabilities (PostCSS inside Next.js is pinned to a patched version through an npm override; re-check when upgrading Next).
